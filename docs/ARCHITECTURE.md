# Архитектура БонусПро

Статус: целевая архитектура новой реализации, не описание существующего кода.
Дата: 2026-10-13. Wallet исключён из первого выпуска по решению владельца.
Протоколы МойСклад должны быть сверены с актуальной документацией и проверены реальной установкой; ниже не предполагается существование неподтверждённых API.

## 1. Назначение и границы

Основной сценарий — заказ покупателя, связанные оплаты и отгрузки в МойСклад.
Оператор видит баланс и применяет бонусы в виджете документа.
Администратор управляет правилами, сотрудниками, импортом остатков и проблемами синхронизации.
Отдельная кассовая интеграция, фискализация, QR-оплата и Wallet не входят в выпуск 1.
Loyalty API не включается в дескриптор только на основании названия продукта.
Источником истины о продажах служит МойСклад, о бонусных проводках — PostgreSQL БонусПро.

## 2. Технологии и развёртывание

Модульный монолит: Python 3.12, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 17.
Первый реализованный экран администратора: браузерные ES modules и CSS без сборщика. Контракт обмена с host проверяется браузерными тестами. Стек полного виджета выбирается по мере его реализации. Зависимости Python зафиксированы в requirements-server.lock и проверяются pip-audit.
Один кодовый репозиторий, один контейнерный образ API/worker, отдельные процессы.
Reverse proxy Caddy завершает TLS. Только 80/443 публичны для приложения.
PostgreSQL и порт API не публикуются наружу.
Фоновая очередь, outbox/inbox и блокировки находятся в PostgreSQL; Redis и микросервисы пока не нужны.
Это снижает сложность и расход памяти на небольшом VPS.
Сборка образа и тесты выполняются вне сервера заказчика; сервер получает образ по digest.
Ресурсы и параллельность worker ограничиваются; пригодность 2 GB RAM подтверждается нагрузочной проверкой.
Старое приложение не заменяется до резервной копии, проверки восстановления и контролируемого переключения.

## 3. Модули и зависимости

Планируемая структура:

    backend/bonuspro/
      domain/          # деньги, правила, проводки, состояния, без HTTP/ORM
      application/     # сценарии, транзакционные границы, порты
      adapters/
        moysklad/      # Vendor lifecycle, REMAP, контекст виджета
        postgres/      # psycopg, репозитории, outbox/inbox, очередь
      api/             # HTTP, валидация, сессии, авторизация
      worker/          # задания, сверка, восстановление операций
      observability/   # структурные логи, метрики, редактирование секретов
    frontend/
      widget/          # интерфейс заказа
      admin/           # административный интерфейс
      shared/          # доступные компоненты, типы, клиент API
    migrations/
    tests/{unit,integration,contract,e2e}/
    deploy/
    docs/

Domain не импортирует HTTP или ORM. API не изменяет баланс напрямую.
Все финансовые изменения проходят application-сценарии и одну транзакцию БД.
HTTP-контракты проверяются API- и браузерными тестами. OpenAPI production endpoint отключён; генерация типизированного клиента для полного виджета ещё не реализована.
Изменения схемы имеют миграции; create_all не используется при production startup.

## 4. Модель данных и инварианты

Все бизнес-сущности имеют tenant_id.
Ключи и внешние ссылки составные: (tenant_id, entity_id), чтобы БД запрещала межмагазинные связи.

- tenants: внутренний магазин и подтверждённый accountId МойСклад.
- installations: состояние установки, appId, поколение установки, зашифрованные credentials.
- principals/roles: проверенная внешняя идентичность и локальные разрешения.
- customers/customer_links: внешний ID контрагента; телефон не является уникальной идентичностью.
- rule_versions: неизменяемые версии правил и момент начала действия.
- orders/order_snapshots/order_lines: внешние ID, суммы, подтверждённое состояние и снимки строк.
- wallets: сериализация операций клиента; materialized balance сверяется с журналом.
- ledger_transactions/ledger_postings: неизменяемые знаковые целочисленные проводки.
- reservations: активные резервы, сумма, состояние и срок пересмотра.
- redemption_operations: состояние связи резерва со скидкой во внешнем документе.
- sales_allocations: связь строк заказа, отгрузок, оплат и возвратов.
- inbox_events/outbox_jobs: устойчивое принятие и обработка событий.
- reconciliation_cases: неоднозначные документы и действия для исправления.
- import_batches/import_rows: проверяемый перенос остатков.
- audit_events: кто, когда и почему менял настройки или выполнял корректировку.

Одна ledger transaction сбалансирована между клиентским и системным бонусным счётом.
Журнал не редактируется и не удаляется; исправления — новые компенсирующие проводки.
Суммы денег — целые минимальные денежные единицы (для KZT: 100 на 1 ₸), бонусы — целые единицы.
Никаких binary float в финансовых расчётах. Проценты хранятся целыми basis points.
Списание не превышает баланс минус активные резервы и лимит текущего заказа.
Операции блокируют кошелёк в фиксированном порядке; проверки и проводки атомарны.
Уникальный ключ (tenant, operation_kind, idempotency_key) защищает от дублей.
Повтор того же ключа с иным payload возвращает конфликт, а не чужой успешный результат.
Timeout клиента не означает неуспех операции: результат запрашивается по operation_id.
Сериализуемый бизнес-эффект обеспечивается транзакциями и уникальностью, а не обещанием exactly-once доставки.

## 5. Подтверждённая финансовая логика

1 бонус = 1 ₸. Бонусы бессрочны.
Начальные правила: начисление 5%, максимальное списание 30%; значения регулируются.
База начисления — стоимость до бонусного списания. Начисление округляется вниз до целого бонуса.
Начисление возможно только после полной оплаты И полной отгрузки.
Изменение глобальных правил не переписывает старые операции.
Версия правил фиксируется при вступлении заказа в бонусный сценарий и видна в аудите.
Исторические продажи не подключаются к начислениям автоматически.
Остатки из БонусПлюс импортируются отдельными проводками, а не повторным начислением покупок.

Пример: исходная допустимая сумма 10 000 ₸, списано 2 000 бонусов, к оплате 8 000 ₸.
После подтверждения всей оплаты и всей отгрузки начисляется 500 бонусов.

Необходимо зафиксировать продуктовые решения до production включения:
- база после обычных скидок, участие доставки/услуг/исключённых товаров;
- определение момента фиксации правил для заказов, созданных до изменения правил;
- политика сопоставления контрагентов и переноса отрицательных остатков.

До утверждения этих решений такие случаи блокируются с понятной причиной, а не получают придуманную финансовую обработку.
Утверждено 13.10.2026: автоматический отрицательный баланс запрещён. Если свободных бонусов для отмены начисления не хватает, создаётся дело администратора. Он может отменить начисление после восстановления остатка либо сохранить бонусы клиенту с обязательной причиной. До решения новые резервы блокируются; существующие сверяются. Денежная сумма возврата не изменяется этим решением.

## 6. Списание и сохранение скидки

Состояния: reserved -> applying -> verifying -> committed.
Возможные ветви: cancelled, expired (только после безопасной сверки), reconciliation_required.
Откат после committed выполняется компенсирующей операцией, не сменой старой проводки.

1. Сервер проверяет подписанный/доверенный контекст установки и пользователя, tenant и права.
2. Читает сохранённый заказ из МойСклад; определяет допустимость и текущие обычные скидки.
3. Рассчитывает quote, связанный с хешем финансовых полей, клиентом и версией правил.
4. Подтверждение создаёт резерв атомарно с записью задания.
5. Адаптер применяет скидку только через подтверждённый механизм МойСклад.
6. После сохранения сервер повторно читает документ и сверяет клиент, строки, суммы и распределение скидки.
7. Только подтверждённая скидка переводит резерв в списание.

Сигнал браузера «сохранено» не является доказательством скидки.
Нельзя держать транзакцию БД открытой на время внешнего HTTP.
После timeout записи сначала перечитать документ; не повторять слепо изменение.
Истёкший резерв нельзя освобождать, пока возможно наличие сохранённой внешней скидки.
Закрытие вкладки не оставляет необнаружимый резерв: worker сверяет незавершённые операции.
Перед перезаписью проверяется снимок документа; чужие изменения не затираются.
Если API не предоставляет надёжную условную запись, это явно компенсируется повторной сверкой и обнаружением конфликтов.
Несохранённые изменения строк/клиента требуют сохранения документа и нового расчёта.
Доступность бонусов уменьшается на резерв сразу; интерфейс отдельно показывает резерв и подтверждённое списание.
Удаление бонусной скидки после списания выявляется сверкой и обрабатывается по финансовому состоянию заказа.

Распределение бонусной скидки по строкам детерминированное, в минимальных денежных единицах, с точным итогом.
Обычные скидки сохраняются. Возвраты используют исходное распределение, а не новые цены.
Если МойСклад не позволяет представить скидку без искажения итогов/налогов, операция блокируется до явного решения.
Не использовать неподтверждённые поля API или скрытую подмену цен.

## 7. Оплаты, отгрузки, отмены и возвраты

Вебхуки — сигнал для перечитывания документов, не достоверная финансовая запись.
События могут дублироваться, запаздывать и приходить в ином порядке.
Приёмник сохраняет inbox и быстро отвечает; worker объединяет задания по заказу.
Очередь имеет lease, повтор с backoff/jitter, лимит попыток и видимый список ошибок.
Периодическая сверка по перекрывающимся временным окнам дополняет вебхуки.
Пагинация обязательна; состояние курсора сохраняется после устойчивой обработки.
Полный контрольный проход выполняется периодически и после восстановления из backup.

Сопоставление оплат учитывает фактические связи, проведение/отмену документа, валюту, распределение на несколько продаж.
Не суммировать повторно одну оплату через заказ и отгрузку.
Предоплата, переплата и ручной статус «оплачен» сами по себе не доказывают полную оплату нужного заказа.
Отгрузка проверяется по соответствующим строкам и количествам, не только общей сумме.
Несвязанные документы, изменение клиента/валюты и неоднозначные возвраты создают reconciliation_case.
Неполная оплата или отгрузка не начисляют бонусы в выпуске 1.

После изменения документов рассчитывается целевое право на начисление; в журнал проводится только разница.
Частичный возврат пересчитывает совокупное право по оставшимся строкам с единым округлением; не округлять независимо каждый повторный возврат.
Полный возврат приводит к точному обратному эффекту первоначальных начисления и списания.
Возврат списанных бонусов распределяется по возвращённым строкам и исходной скидке.
Денежный возврат не увеличивается на бонусы.
Отмена проведения, удаление и исправление документов рассматриваются отдельно от нового заказа.
Параллельная работа БонусПлюс и БонусПро с двойным начислением при переходе исключается организацией cutover.

## 8. Установка и авторизация

Один tenant создаётся из проверенного accountId установки, а не из параметра браузера.
Install/update/uninstall idempotent; повторная установка имеет явную политику старого журнала.
При отключении прекращаются внешние записи и задания, credentials отзываются/деактивируются, история сохраняется по политике хранения.
Подписи, алгоритмы, срок токенов, issuer/audience и защита от replay реализуются по реально подтверждённому протоколу Vendor API.
Не изобретать собственный HMAC в качестве замены проверки протокола поставщика.
Права REMAP минимальны; финальный descriptor соответствует только реализованным возможностям.
Контекст виджета проверяется сервером. postMessage проверяет origin, source, схему и привязку к текущему iframe.
В iframe не передаются токен REMAP и долгоживущие секреты.
Поведение с заблокированными third-party cookies проверяется отдельно; не ослаблять auth ради iframe.
Прямой переход по URL виджета без валидного контекста не даёт доступ к данным.

Роли: оператор, менеджер, администратор. Ручная корректировка ограничена правами и требует причины.
Сервер проверяет разрешение для каждой команды независимо от видимости кнопок.
Административные сессии короткие, отзывные; чувствительные действия требуют повторного подтверждения личности.
CSRF для cookie-команд, ограниченный CORS, CSP с точными frame-ancestors, безопасные cookies при применимости.
Не полагаться на глобальный X-Frame-Options DENY для встроенного виджета.

## 9. Защита данных и сети

Секреты вне Git/образов/frontend; credentials магазинов шифруются аутентифицированным шифрованием с key version.
Главный ключ хранится отдельно от БД; описывается безопасная ротация и восстановление ключей.
Логи удаляют Authorization, cookies, токены, персональные payload и query secrets.
Webhook URL не является достаточным доказательством доверия.
Доверенные внешние адреса фиксированы; meta.href не используется для произвольных запросов: проверяются HTTPS, host, path и отсутствие перенаправления к посторонним адресам.
Таймауты, ограничения размера, per-tenant rate limit, обработка 429 и лимиты параллельности обязательны.
Ни один tenant не может занять всю очередь.
PostgreSQL RLS с FORCE и ролью без BYPASSRLS дополняет tenant-фильтры и составные FK.
SET LOCAL tenant context только внутри транзакции; повторное использование pool connection не переносит контекст.
Миграции выполняются отдельной привилегированной ролью.
Health-check не раскрывает credentials, номера клиентов и stack traces.
Пользовательские имена и HTML отображаются безопасно; CSV export защищён от formula injection.
Backup шифруется, отправляется вне VPS, имеет ограниченные права и периодическую проверку восстановления.

## 10. UX

Светлый интерфейс, без рекламного заголовка и имитации МойСклад.
Виджет: клиент, доступный баланс, резерв, максимум списания, ввод суммы, сумма к оплате, одна основная команда.
Успех появляется только после серверного подтверждения. Ожидание и конфликт имеют отдельные состояния.
Нет бесконечного спиннера: таймаут показывает «Проверяем результат» и номер операции.
Ошибки понятны сотруднику и содержат действие; технические детали остаются в диагностике.
Клавиатура, фокус, подписи полей, контраст, screen-reader status и небольшая ширина iframe проверяются.
Панель: клиенты/журнал, правила, интеграция, импорт, проблемные операции.
Изменение правил показывает, какие новые операции оно затронет.
Импорт имеет предпросмотр, дубли/ошибки, итоговые суммы и подтверждение пакетного применения.

## 11. Эксплуатация

Метрики: возраст очереди, время последней успешной сверки, ошибки API, резервы без подтверждения, расхождения журнала, возраст backup.
Liveness отличается от readiness; отказ МойСклад не выдаёт ложное отсутствие сохранённой операции.
Развёртывание: backup -> миграция с lock -> запуск -> readiness -> smoke -> переключение.
Миграции обратно совместимы в пределах окна отката; не обещать автоматический rollback схемы с потерей данных.
Сервис запускается non-root, с ограничением capabilities, tmpfs и read-only FS где возможно.
Docker socket внутрь приложения не монтируется.
Восстановление БД репетируется на изолированной среде; повторная внешняя сверка обязательна, чтобы не повторить скидки после отката БД.
Плановые RPO/RTO согласуются по результатам реального теста, не объявляются достигнутыми заранее.
Локальные backup на том же диске не считаются полноценным аварийным восстановлением.
