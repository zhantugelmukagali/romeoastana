# Правила и критерии выпуска

Это спецификация приёмки. Ни один пункт не считается выполненным без результата теста и ссылки на проверенный commit/image digest.

## Подтверждённые правила

- Заказы покупателей и отгрузки; расширение в МойСклад.
- Начальное начисление 5%, предельное списание 30%; настройка процентов.
- База начисления до бонусного списания, 1 бонус = 1 ₸, целые бонусы вниз.
- Начисление только после полной оплаты И полной отгрузки.
- Бессрочные бонусы; пересчёт при возврате.
- Wallet после первого выпуска.
- Старые покупки автоматически не начислять.
- Светлый рабочий интерфейс, без рекламных текстов.

## Финансовые сценарии

| Сценарий | Ожидаемый результат |
| --- | --- |
| Заказ 10 000 ₸, списание 2 000, оплачено 8 000, всё отгружено | Списание 2 000, начисление 500 один раз |
| Оплачен, но не отгружен полностью | Начисления нет |
| Отгружен, но частично оплачен | Начисления нет |
| Несколько оплат и отгрузок | Связи учтены без повторного включения сумм |
| Недостаточно доступных бонусов | Резерв/списание отклонены атомарно |
| Два заказа параллельно используют один баланс | Совокупный резерв не превышает доступный баланс |
| Применена скидка, ответ API потерян | Повторное чтение и восстановление результата без дубля |
| Пользователь закрыл виджет после применения скидки | Worker завершает сверку |
| Истёк резерв, состояние скидки неизвестно | Резерв не освобождается вслепую |
| Заказ изменён между расчётом и сохранением | Новый расчёт; чужие изменения не затираются |
| Смена клиента при активном резерве | Старый расчёт нельзя применить другому клиенту |
| Повторный/переставленный webhook | Итоговые проводки неизменны |
| Частичный возврат | Пересчёт оставшегося права и возврат исходного списания по строкам |
| Несколько частичных возвратов до полного | Точный итог полного возврата без потери округлений |
| Возврат начисления, уже потраченного в другом заказе | Только утверждённая политика долга; нельзя молча обнулить баланс |
| Отмена/удаление оплаты или отгрузки | Сверка права на бонусы, корректирующая проводка |
| Ручная корректировка | Права, причина, аудит, идемпотентность |
| Изменение правил | Старые операции не переписываются |
| Повтор импорта одного пакета | Нет повторного зачисления |

## Уровни тестирования

1. Unit: целочисленная арифметика, границы ставок, округление, распределение остатка по строкам.
2. Property-based: сохранение сумм распределения, детерминированность, монотонность начисления, полный возврат = исходному обратному эффекту.
3. PostgreSQL integration: транзакции, блокировки, конкурентные списания, unique/FK/RLS, rollback, tenant context в пуле.
4. Contract: сохранённые обезличенные fixtures API, ошибки/таймауты/пагинация/429, подписи и lifecycle. Fixtures не заменяют реальную интеграцию.
5. Fault injection: остановка после каждого шага saga, потерянный ответ, недоступный API/БД, повтор job после lease.
6. Browser: клавиатура, узкий iframe, подтверждение сохранения, несохранённые изменения, закрытие вкладки, две вкладки, third-party cookies.
7. Real integration: установка на отдельном аккаунте, реальный заказ/оплата/отгрузка/возврат/отмена/переустановка.
8. Deployment: новый VPS-эквивалент, миграции, HTTPS, health/readiness, rollback, backup/restore, повторная сверка после restore.

Тесты финансовых транзакций не подменяются SQLite.
Результаты указывают commit, среду, количество проверок и непроверенные сценарии.
Security scan без проверки бизнес-авторизации не означает «безопасно».

## Безопасность — обязательные отрицательные проверки

- Чужой tenant/customer/order/operation ID: доступа нет.
- Контекст установки с неверной подписью, истёкшим сроком, неверным назначением: отказ.
- Replay и повтор отключённой установки: нет повторных эффектов.
- Оператор вызывает административный endpoint напрямую: отказ.
- CSRF, недоверенный postMessage origin/source и неподходящий CORS origin: отказ.
- API meta.href указывает на посторонний/внутренний адрес: запрос не выполняется.
- Неизвестный алгоритм токена, пустая конфигурация секрета: fail closed.
- Секреты отсутствуют в frontend bundle, исходниках, логах, ответах и CI artifacts.
- SQL-пользователь приложения не обходит RLS; pooled connection не переносит tenant.
- Import CSV с формулами, дублями, неверной валютой/суммой: безопасная обработка.
- Rate limiting не позволяет одному магазину блокировать остальные.

## UX — проверяемые критерии

- Баланс, допустимая сумма, сумма к оплате и статус операции видны без перехода в отдельную панель.
- «Списано» показано только после подтверждения сохранённой скидки.
- Повторное нажатие/перезагрузка не создают новую финансовую операцию.
- Ошибка не очищает введённую сумму без причины; следующий шаг понятен.
- Состояния загрузки, резерва, проверки, успеха, конфликта и недоступности различимы.
- Формы работают с клавиатуры; фокус и ошибки доступны screen reader.
- На типовой ширине встроенного виджета нет горизонтальной прокрутки основного сценария.

## Импорт и переход

Экспорт БонусПлюс сначала проверяется: магазин, идентичности клиентов, валюта, баланс, дубли, контрольные суммы.
Телефон не используется для автоматического слияния неоднозначных клиентов.
Dry-run показывает распределение ошибок и итоговую сумму.
Импорт имеет batch ID, неизменяемый аудит и повторяемую проверку.
На момент перехода фиксируются граница операций и ответственность старой/новой системы.
Возможность отключить новые операции не должна удалять уже подтверждённый журнал.

## Блокирующие выпуск условия

- Не согласованы финансовые пограничные случаи.
- Не проверен актуальный протокол МойСклад и реальная установка.
- Есть расхождения внешней скидки и журнала без процесса исправления.
- Не выполнена репетиция backup restore вне рабочей базы.
- Нет мониторинга ошибок и просроченной синхронизации.
- Не проверены миграции и обратимость конкретного релиза.
- Не пройдены интеграционные/конкурентные/браузерные проверки.
- Нет закреплённых владельцем каналов поддержки и процедуры инцидента.

Публикация каталога и включение магазину — разные события.
Наличие APK/Wallet, видео или маркетинговой карточки не заменяет финансовую приёмку.
