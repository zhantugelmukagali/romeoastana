# Возвраты и отмены без отрицательного баланса

Подтверждено владельцем: недостаток бонусов при возврате разбирает администратор.
Схема 0009 добавляет накопительный пересчёт по сохранённым позициям REMAP.

## Пересчёт

Worker дважды читает граф заказа, оплат, отгрузок и связанных salesreturn.
Проверяются аккаунт, стороны, валюта, НДС, ассортимент/цена/скидка/упаковка и количества.
Сумма возвращённых количеств не может превышать соответствующую отгрузку.
Непроведённый возврат не участвует; изменение/отмена проведения пересчитывается.

Начисление после полного исполнения хранится как исходная неизменяемая величина.
После возврата рассчитывается право по оставшимся товарам до бонусной скидки.
Списанные бонусы возвращаются по исходному распределению на возвращённые позиции.
Накопительный расчёт через рациональные доли исключает потерю округлений между частичными возвратами.
При полном возврате получается исходная сумма обратного эффекта.
Отмена возврата восстанавливает начисление и отменяет ранее возвращённое списание.
Отмена полной оплаты/отгрузки убирает право на начисление; восстановление возвращает его.

settlement_events фиксирует целевые суммы, изменения обеих частей, evidence hash, автора и причину.
Одна нетто-проводка отражает итог баланса; взаимно погасившиеся изменения также остаются в аудите.
Повтор доказательства не создаёт вторую операцию. Существующий резерв не расходуется возвратом.

## Нехватка бонусов

При недостатке свободных бонусов появляется settlement_case, баланс не меняется.
Новые списания по клиенту блокируются; уже подготовленные операции остаются для проверки.
Администратор может:
- выполнить пересчёт после восстановления достаточного свободного остатка;
- сохранить бонусы клиенту, указав причину: отрицательные компоненты прощаются,
  положительные сохраняются.

Решение заново проверяет документы. Устаревшая карточка не применяется.
Последующее пополнение само не закрывает pending: нужно решение администратора.
Прощённая часть учитывается при последующей отмене/повторе возврата;
новые дополнительные возвращённые позиции не получают автоматического прощения.
Старые записи никогда не редактируются.

## Исправление заказа

Изменение сохранённой финансовой основы/метки после начисления создаёт расхождение.
После восстановления исходных данных администратор нажимает «Проверить исправление».
Сервер перечитывает документы; закрытие хранит автора/причину.
Повторное расхождение после закрытия создаёт новый эпизод.

## Неподтверждённое списание

Схема 0013 позволяет админу освободить verifying-резерв только когда:
- прошло не менее 15 минут с подготовки;
- все вкладки заказа закрыты, заказ отменён (снят с проведения);
- сервер подтвердил исходные цены/строки/стороны и отсутствие бонусной метки;
- нет проведённых оплат, отгрузок, возвратов, связей со счетами/предоплатами,
  мешающих доказать отсутствие оплаты.

Проверка идёт по актуальному графу, не по флажку браузера.
История отмены неизменяема; прямой переход verifying -> released без неё запрещает БД.
Подтверждённое списание этим действием не отменяется.
При позднем сохранении старой метки деньги не списываются вслепую:
заказ выделяется как расхождение, новые списания по клиенту блокируются.
Это обнаружение конфликта при следующей сверке, не условная атомарная запись в МойСклад.
Для активного заказа без доказанной отмены произвольного освобождения резерва нет.

Старый Returns/return_cases сохранён для прежней внутренней модели и её истории.
Новая автоматическая обработка использует Settlements; два механизма не вызываются на один возврат.
