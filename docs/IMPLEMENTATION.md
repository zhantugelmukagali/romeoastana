Браузерный host МойСклад в UX-тестах имитируется; это не реальная установка.
Проверка backup/restore относится к тестовой непустой БД, а не backup VPS заказчика.
Аудит зависимостей проверяет известные Python-уязвимости на момент запуска,
а не доказывает отсутствие всех уязвимостей кода и образа.

## Реализовано

- Часть 1 [плана выпуска](DELIVERY_PLAN.md): /settings, административный API правил,
  неизменяемые версии с причиной/автором, защита от устаревших и повторных изменений.
- Связь UUID контрагента со счётом, фиксация правил в заказе и внутренний preview,
  учитывающий резервы и административный разбор возвратов; теперь подключён к API виджета.
- Политика первого выпуска: только товары, доставка исключена. Реальная классификация
  позиций реализована по типу assortment: product/variant/bundle участвуют, service исключён.
  Доставка должна быть услугой в учётной системе. Подробнее [CHECKOUT.md](CHECKOUT.md).

- Часть 2: /widget, чтение настоящего сохранённого заказа, расчёт с обычными скидками,
  атомарный резерв с неизменяемым планом, UpdateRequest и подтверждение через повторное чтение REMAP.
  Баллы списываются только при совпадении строк, клиента, организации, НДС, валюты, суммы и метки.
  UpdateResponse/Save из браузера сами по себе не подтверждают финансовую операцию.
- Повтор prepare возвращает прежнюю операцию без повторной отправки изменений формы;
  параллельные verify дают одну проводку; неизвестный результат удерживает резерв.
- Настройка собственного поля операции из /settings. Вариант descriptor-widget.xml
  проверен по официальной XSD; рабочая установка по-прежнему не проверена.
- Виджет сбрасывает старый заказ при повторном Open, игнорирует чужие сообщения,
  блокирует применение к несохранённым изменениям и не показывает успех до проверки.
  Маршруты документов пока доступны администратору; обычные сотрудники не получают
  автоматически расширенные права токена приложения.
- Целочисленные расчёты, лимиты, распределение скидки.
- PostgreSQL: FORCE RLS, составные FK, неизменяемый сбалансированный журнал.
- Идемпотентные зачисления/резервы; блокировки кошелька; списание по внутреннему
  контракту подтверждённой скидки. Неизвестный внешний результат сохраняет резерв.
- Vendor lifecycle Install/Resume/Suspend/Uninstall: JWT HS256, jti против replay,
  шифрование REMAP token AES-GCM с привязкой к tenant, поколение установки.
- Одноразовый user context меняется на сервере на собственную сессию; роли сотрудника
  подтверждает Vendor API. Suspend/Uninstall отзывают сессии.
- Отмена начисления по UUID возврата: проводка либо дело администратора без долга.
  Pending блокирует новые резервы; решение администратора сохраняет причину и автора.
- Экран возвратов: белый интерфейс, состояния/история, подтверждение, обязательная
  причина, блокировка недоступного списания, ошибки, повтор, пагинация, мобильная ширина.
- PostgreSQL jobs: транзакционная постановка/подтверждение, SKIP LOCKED,
  аренда с fencing token, повтор с задержкой, предел попыток, dead.
- REMAP GET: фиксированный API host, проверка id/accountId, Decimal, регион kz,
  полная пагинация позиций, защита от внешних ссылок и классификация ошибок/429.
  OrderEvidence не подменяет прикладную финансовую сверку; см. REMAP.md.
- HTTP: проверка Origin/Host, ограничение тела, CSP, no-store, скрытие секретов
  из ошибок; административный API не принимает роль, автора или сумму из браузера.
- Контейнер non-root/read-only, явные миграции отдельной ролью, файловые секреты.
- CI: функциональные, конкурентные, HTTP, браузерные тесты, контейнерный запуск,
  восстановление БД, lock-файл и pip-audit.

## Что блокирует выпуск

Это существенная недостающая реализация, а не только ожидание доступа:

1. Приёмка виджета в настоящем МойСклад: поля/маркер, права, штатные скидки,
   конкурентное редактирование и округления. Реализованный путь описан в [WIDGET.md](WIDGET.md).
   Не все заказы поддерживаются: например, НДС сверху и скидки, которые нельзя точно
   выразить шагом 0,01%, отклоняются. Это ограничение выпуска, а не автоматическое округление бонусов.
2. Явная политика допуска обычных сотрудников и проверка их прав. Сейчас только admin.
3. Worker/планировщик, события, автоматические начисления по полной оплате И отгрузке,
   повторная сверка и восстановление потерянного ответа. Неподтверждённый резерв
   пока не имеет завершённого административного сценария отмены/разблокировки.
4. Возврат ранее списанных бонусов по строкам, изменение/отмена документа возврата,
   восстановление начисления после исправлений. Нужен полный цикл, а не только журнал.
5. Завершение настройки и переход SettingsRequired -> Activated после частей 3–4.
   Текущий код НЕ включает рабочие продажи при сохранении правил или подготовке поля.
6. Импорт остатков БонусПлюс с dry-run, дублями, сверкой и безопасным переключением.
7. Настоящая установка/обновление/отключение и полная приёмка на аккаунте разработчика.
   appId/appUid предоставлены; ввод Secret Key на VPS подтверждён владельцем.
8. Ограничение частоты запросов/квот, мониторинг, очистка истёкших сессий/replay,
   ротация ключей, независимый backup VPS и репетиция восстановления/переключения.
9. Проверка нагрузки на VPS 2 GB и эксплуатационная поддержка.

Wallet не включён в первый выпуск по решению владельца.
