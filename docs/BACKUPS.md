# Резервные копии БонусПро

Код резервирования подготовлен. На VPS таймер ещё не включён и отдельного хранилища
у владельца пока нет. Копия на том же сервере не защищает от потери VPS.

## Что делает копирование

scripts/backup_vps.py запускается только root. pg_dump читает согласованный снимок
PostgreSQL. Вывод шифруется в отдельном изолированном контейнере приложения, без сети,
привилегий, доступа к БД или секрету Vendor API. Образ задан неизменяемым тегом.
Частичный файл не публикуется при ошибке pg_dump, шифрования или записи.

Формат BPBK0001 использует AES-256-GCM и отдельный HKDF-ключ для каждого файла.
Размер блока ограничен 1 МиБ. Заголовок, номера блоков и финальная запись
аутентифицированы. Обнаруживаются повреждение, неверный ключ, перестановка блоков,
обрезанный хвост и лишние байты. Это прикладной формат; он не заменяет инфраструктурный аудит.

Мастер — существующий TOKEN_ENCRYPTION_KEY. Производный ключ имеет другое назначение.
Мастер должен иметь независимую защищённую копию вне VPS. Файл SQL не содержит
этого ключа: без него копию расшифровать нельзя. vendor_secret и .env.release также
сохраняются отдельно, в защищённой копии конфигурации. В чат секреты не отправлять.

## Ручная проверка после обновления до версии с backup_stream

sudo python3 scripts/backup_vps.py --image-from-env

Команда сообщает путь к файлу .pgdump.bpbk и контрольную сумму; она не утверждает,
что копия уже перенесена наружу или восстановлена.

sudo python3 scripts/verify_backup_vps.py /home/ubuntu/bonuspro-backups/encrypted/ИМЯ.pgdump.bpbk --image bonuspro:КОММИТ --expected-schema 0014

Проверка сначала полностью расшифровывает файл в закрытый временный файл.
Только после успешной аутентификации создаётся отдельная временная БД.
pg_restore должен завершиться без ошибок; проверяются версия схемы и баланс проводок.
Рабочая bonuspro не перезаписывается. Временная БД удаляется. Проверка не отправляет
запросов в МойСклад. ENCRYPTED_BACKUP_RESTORE_OK относится именно к этой копии.
Проверка роли RLS в восстановленной БД дополнительно выполняется в контейнерном CI.

## Расписание

В deploy есть bonuspro-backup.service и bonuspro-backup.timer.
Они используют /home/ubuntu/bonuspro-release и текущий тег из .env.release, не выполняют
git pull и не меняют конфигурацию. UTC-расписание: ежедневно около 03:00 плюс до
15 минут случайного сдвига. На VPS нужно установить файлы в /etc/systemd/system,
выполнить daemon-reload, enable --now таймера и проверить первый запуск.

Расписание — пример, а не согласованный RPO. Для магазина согласовать частоту,
хранение, размер и оповещение. Автоматическое удаление копий намеренно не включено,
пока не подтверждены независимая копия и политика хранения. Контролировать диск.

## Условия выпуска

1. Защищённая офлайн-копия ключа и конфигурации.
2. Независимое хранилище и автоматическая доставка туда зашифрованных файлов/контрольных сумм.
3. Проверенное восстановление скачанной внешней копии на отдельной машине.
4. Оповещения о сбое задания, отсутствии свежей внешней копии и заполнении диска.
5. Регулярная проверка восстановления и ротация ключей с сохранением старых ключей
   для ранее созданных файлов.

Пункты 2–4 не настроены одними файлами systemd. Нужны выбранное хранилище,
учётные данные и канал оповещения. Потеря VPS вместе с единственным ключом делает
восстановление невозможным.
