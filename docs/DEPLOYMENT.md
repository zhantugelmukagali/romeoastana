# Сборка и изолированное развёртывание

Основная ветка использует схему 0018 и worker-pool профиля marketplace.
Обновление установленного VPS — по [HANDOVER.md](HANDOVER.md), проверка покупок —
по [LIVE_CHECK_RU.md](LIVE_CHECK_RU.md). Сборка контейнера не заменяет финансовую приёмку.

Рабочий пилот на VPS не перезаписывать. Compose имеет отдельное имя проекта
bonuspro-release и отдельный PostgreSQL volume. Старую базу не подключать к
новым миграциям. Порт приложения доступен только на 127.0.0.1:18080.

## Подготовка

Этот раздел предназначен для первой установки в новый изолированный каталог. Для уже работающего VPS используйте раздел обновления и не создавайте секреты повторно.

1. Проверить commit и зелёный CI, собрать неизменяемый тег:
   docker build --pull -t bonuspro:COMMIT_SHA .
2. Указать BONUSPRO_IMAGE, PUBLIC_ORIGIN, MOYSKLAD_APP_ID, MOYSKLAD_APP_UID
   в отдельном файле параметров (идентификаторы из кабинета разработчика).
3. На Ubuntu выполнить sudo python3 deploy/prepare_secrets.py.
   Secret Key вводится скрыто, не через аргументы командной строки.
   Скрипт работает только при отсутствии deploy/secrets и не меняет старые ключи.
4. Сделать зашифрованную резервную копию файлов секретов отдельно от VPS.
   Без TOKEN_ENCRYPTION_KEY сохранённые токены нельзя расшифровать.
   Файлы в secrets не добавлять в Git и не присылать в чат.

Команды Compose ниже дополняются --env-file с подготовленным файлом параметров.

## Первая установка в пустой изолированной БД

Команды ниже не применяют к установленной рабочей БД; для неё используйте обновление
через finish_marketplace.py по HANDOVER.md, сохраняя существующие ключи и историю.

- docker compose -f compose.release.yaml up -d db
- docker compose -f compose.release.yaml --profile maintenance run --rm bootstrap
- docker compose -f compose.release.yaml --profile maintenance run --rm migrate
- docker compose -f compose.release.yaml up -d app

Bootstrap имеет временный административный доступ только для создания ролей.
Миграции выполняются отдельной ролью bonuspro_migrator. Приложению не передаётся
ни административный, ни миграционный пароль. Запуск HTTP не запускает миграции.

Проверить /health/ready на локальном порту с Host из PUBLIC_ORIGIN. Затем
отдельно настроить HTTPS reverse proxy, доверенный origin, ограничение частоты
запросов и наблюдение за ошибками. HTTPS уже переключён владельцем на bonuspro-release-web-1 (compose.https.yaml).
Не менять существующие TLS volumes. Готовое приложение само не запускает пул и не подтверждает финансовую приёмку.

## Обновление установленного VPS

Из проверенного checkout основной ветки на Ubuntu используйте
`sudo python3 deploy/finish_marketplace.py` по [HANDOVER.md](HANDOVER.md).
Поддерживаются установленная совместимая 0015 и основные 0017/0018. Скрипт проверяет
точную структуру БД, копию и восстановление, сохраняет историю и обновляет app
и worker-pool одного образа. Профиль marketplace требует свежей обработки каждого
активированного аккаунта; общий BONUSPRO_TENANT_ID для пула не задаётся.
Режим --prepare-only обновляет выпуск без полной финансовой проверки. Если программа
ещё не запущена, завершите настройку в интерфейсе. Сохранённая активация и дата
начала существующей программы сохраняются; повторный запуск ей не требуется. После изменения схемы или замены app сбой исправляется
вперёд: финансовая БД автоматически не восстанавливается, старый worker не запускается.
Tenant-worker нельзя запускать параллельно пулу.

### Историческое обновление совместимой ветки до 0015

Следующий порядок сохранён для прежнего выпуска одного аккаунта и не является
текущим порядком развёртывания основной ветки. Для того выпуска использовался
deploy/finish_release.py --tenant UUID. Он вызывает проверенное обновление0013/0014→0015,
обновляет worker тем же образом и выполняет read-only проверку реальных документов.
Переход включает защищённый backup конфигурации/ключей/БД, отдельное восстановление
и пробную миграцию до остановки работающих сервисов. Новое приложение проверяется
локально до открытия HTTPS. При сбое до доступа пользователей допустим только
защищённый откат добавленной DDL при отсутствии нового аудита; финансовый журнал
не восстанавливается поверх рабочей БД. После доступа пользователей автоматическое
понижение схемы запрещено. Для уже установленной0015 применяется обновление образа.
Граница запуска и ключи остаются прежними. Отдельный update_cabinet.py по умолчанию
также запускает start_processing.py и подтверждает, что worker использует текущий
образ приложения. CABINET_READY запрещён до этой проверки. Сбой обработки после
открытия HTTPS сохраняет новую схему/образ и возвращает ошибку, а не откатывает
рабочий журнал. Внутренний --defer-processing используется только finish_release.py:
готовность всего выпуска подтверждается после обязательного второго этапа.
Подробности и приёмка: HANDOVER.md.

## Резервирование и обновления

CI проверяет pg_dump/pg_restore непустого журнала в отдельную БД и чтение
восстановленного баланса ролью приложения. Это не проверка копии VPS.

До переноса клиентов обязательны внешний зашифрованный backup PostgreSQL,
тест восстановления на отдельной БД, retention и оповещение об ошибках.
Снимок Docker volume без согласования с PostgreSQL не считать проверенной копией.
Периодичность/RPO/RTO пока не согласованы.

Перед миграцией сохраняется backup. При обновлении образа миграция запускается
отдельно; при неуспехе приложение не переключается. Понижение схемы с финансовой
историей намеренно запрещено. Возврат образа допустим только при совместимой схеме.
Секреты, том БД и код — разные объекты резервирования.

Сборка: non-root UID 10001, read-only FS, cap_drop ALL, no-new-privileges,
ограниченные HTTP concurrency и логи. БД не публикует порт наружу.
Базовые образы должны обновляться и повторно сканироваться перед выпуском.

## Безопасная проверка текущего VPS

В Ubuntu (`ubuntu@47107`) выполните одну строку:

```bash
sudo docker inspect bonuspro-release-app-1 bonuspro-release-worker-pool-1 bonuspro-release-web-1 bonuspro-release-db-1 --format '{{.Name}} | {{.Config.Image}} | restart={{.HostConfig.RestartPolicy.Name}} | {{.State.Status}}{{if .State.Health}} | {{.State.Health.Status}}{{end}}' && curl --http1.1 --max-time 15 --fail -sS -H 'Host: loyalty.addwise.kz' http://127.0.0.1:18080/health/ready && curl --http1.1 --max-time 15 --fail -sS https://loyalty.addwise.kz/health/ready
```

Проверка читает состояния и readiness; не обновляет Git, образ или базу. У приложения и worker-pool должны совпадать образы, оба контейнера должны быть healthy; web — running, db — healthy. Оба HTTP-запроса должны вернуть ready. Свежесть обработки дополнительно смотрят в «БонусПро → Настройки → Подключение». Эти результаты не заменяют проверку реального заказа.

Основная ветка ожидает 0018. Совпадение номера схемы само по себе не доказывает совместимость SQL разных веток. Исторический vps_preflight.py проверяет старый worker одного аккаунта и не является критерием готовности worker-pool. В установленном проекте используется detached checkout; git pull для проверки сервера не требуется.

Перед согласованным обновлением: остановить новые финансовые команды,
сделать и проверить независимую копию БД/ключей, собрать конкретный прошедший CI commit,
остановить app/worker на время миграций, применить миграции, поднять новый app,
проверить local/HTTPS readiness и затем worker-pool по HANDOVER.md.
Техническая готовность пула не заменяет проверку реального заказа.
Не выполнять down -v, не удалять pgdata, не генерировать повторно ключ шифрования.
Откат через downgrade финансовых миграций не поддержан: нужен совместимый образ
либо восстановление согласованной копии с учётом внешних действий после её времени.
