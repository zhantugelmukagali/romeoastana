# Проверка контрактов МойСклад — 19.10.2026

Проверены используемые БонусПро контракты Vendor API, iframe/widget и REMAP.
Это отчёт по исходному коду и автоматическим проверкам. Он не утверждает, что
прочитан каждый endpoint МойСклад или пройдена финансовая приёмка на рабочем VPS.

## Официальные источники

Снимки официальных репозиториев фиксируют документацию, использованную для сверки:

- [Vendor API](https://github.com/moysklad/api-vendor-1.0-doc/tree/e3b41a2eda96b1abd074f4f64712d06f927ec9f5/source/includes):
  аутентификация, процессы установки, обе стороны REST, доступ к JSON API,
  дескриптор, виджеты и их сообщения.
- [REMAP 1.2](https://github.com/moysklad/api-remap-1.2-doc/tree/9b39c2701ee43d663ad1c5105dc2b020a59a7010/md):
  general, restrictions, documents/common_info, customerOrder, demand,
  sales_return, payment_in, payment_out, cashin, cashout, currency, webhook.

Файлы source/includes/_5.2_developer_guide_widgets.md,
_5.3_developer_guide_descriptor.md, _6.1_vendor_api_1.0_authentication.md,
_6.2_vendor_api_1.0_processes.md, _6.3_vendor_api_1.0_REST_vendorside.md и
_6.4_vendor_api_1.0_REST_moyskladside.md задают используемый протокол.
Документация может меняться: эти снимки не отменяют дальнейшую проверку изменений API.

## Исправленные пропуски

| Контракт | Прежнее поведение | Исправление и регрессия |
| --- | --- | --- |
| Vendor требует gzip | Вызов подтверждения активации полагался на заголовки библиотеки | Явные gzip и JSON UTF-8; строгий транспорт возвращает 415 без gzip. tests/server/test_vendor_activation.py |
| TariffChanged / Autoprolongation без access_token | Модель допускала только Install / Resume и отклоняла уведомление | Раздельная валидация; уведомление сохраняет токен, поколение сессий, конфигурацию и журнал. tests/integration/test_vendor_lifecycle_contract.py |
| PermissionsChanged без нового токена | Событие не объявлялось и не имело обработчика | additionalEvents/updatePermissions, подписанный PUT /event, оба варианта пути из документации; повтор JWT отклоняется, неизвестная установка не создаётся. Тот же файл тестов |
| Resume сохраняет рабочую настройку | Всегда требовалась настройка заново | Возврат Activated только при совпадении ранее подтверждённых правил и служебного поля; новый токен и отзыв старых сессий; исходная дата начала начислений неизменна. Тот же файл тестов |
| Для черновика лимит 11 запросов / 3 с | Фоновые и длительные административные чтения имели интервал 0,15 с | Интервал 0,35 с в этих сериях. Ответ 429 по-прежнему откладывает сохранённое задание по заголовкам сервера без потери курсора; одновременные окна тоже могут расходовать лимит |

Изменение дескриптора в Git не применяется автоматически к установленному решению.
Нужно сохранить текущий marketplace/descriptor-widget.xml в кабинете разработчика
и обновить установленную версию. Перевыпуск секретного ключа для этих изменений не нужен.

## Сверка реализованного протокола

| Область | Реализация / проверка |
| --- | --- |
| Подпись, назначение, время, replay | security.py, installations.py; server authentication tests и integration/test_installations.py. Секреты и тела JWT не выводятся |
| Контекст сотрудника | vendor.py, web/assets/host.js и bridge.js. Ключ контекста используется для серверного обмена; ответы принимаются с доверенного origin и зарегистрированного окна хоста, включая GWT iframe |
| Create / Edit / Save / Change | Новый несохранённый заказ не списывает бонусы; отдельный контекст edit; изменение заказа инвалидирует расчёт. tests/browser/test_widget.py |
| UpdateRequest | Передаются все исходные id позиций, включая услуги: хост заменяет коллекцию. Изменяется рассчитанная скидка товаров либо, когда точный процент невозможен, их цена в целых денежных minor units; обычная скидка при изменении цены сохраняется. Служебное поле связывает операцию; факт UpdateResponse не считается подтверждением списания |
| Подтверждение списания | Повторное чтение сохранённого заказа, совпадение клиента, товаров, скидки и маркера; одна операция и один дебет. Проверка подтверждённой операции разрешена после последующей оплаты/отгрузки |
| Права | Обычные документы читаются токеном решения. Собственное поле — useOwnAttributeMetadata. Изменение заказа выполняет хост с правами сотрудника. API повторно проверяет роль/разрешение оператора; own webhooks объявлены отдельно |
| Метаданные поля | Точная сущность и тип string, одно необязательное поле, сериализация подготовки, повтор после потерянного ответа без дубликата. Допускается документированный полный список без size и безопасное эхо limit/offset в meta.href |
| HTTP REMAP | Фиксированный HTTPS api.moysklad.ru, JSON UTF-8, gzip, регион kz, ограничение размера/времени, точный Decimal JSON. Чужие href, redirect и nextHref не получают токен |
| Ошибки и повтор | 401/403 отделены от временной недоступности. 429 учитывает миллисекунды X-Lognex-Retry-After/Reset и секунды Retry-After; задание остаётся в БД. Ошибка не превращается в успешное начисление |
| Коллекции | Пагинация строится локально; неполный/меняющийся список, дубль id и чужой accountId не принимаются за полный заказ. У currency accountId необязателен по официальному контракту |
| Время | created/updated МойСклад интерпретируются как MSK, фильтры формируются в MSK; граница программы хранится как абсолютное время. Старые покупки не получают новое начисление |
| Оплата и отгрузка | Проведённые документы, агент/организация/валюта, явные allocations linkedSum, сопоставление всей корзины и два чтения графа. payedSum/shippedSum сами по себе не доказывают исполнение |
| Деньги | KZT, точные minor units, целые бонусы вниз. Только товары/модификации/комплекты; услуги, включая доставку, не участвуют. Начисление после обычной скидки, до бонусной скидки |
| Возврат | Проведённый возврат связан с конкретной отгрузкой, количество не превышает исходное; накопительный пересчёт исключает повторное списание и потерю округления. Недостаток бонусов передаётся администратору без автоматического долга |
| UI | Нулевой баланс без неработающей формы; при доступном балансе — сумма, максимум, итог и одна кнопка. «Списано» только после verified=true. Условия скрыты до раскрытия; размеры create/edit заданы дескриптором |
| Изоляция | PostgreSQL RLS, отдельная роль lifecycle, проверка поколений сессий, блокировки кошелька, идемпотентные проводки и задания; конкурентные тесты выполняются на PostgreSQL |

Сумма баланса поступает из собственного журнала БонусПро по UUID контрагента
внутри аккаунта МойСклад, за вычетом активных резервов. Телефон используется для
поиска, но не для неявного объединения клиентов. Остаток прежней бонусной системы
появится только после проверенного импорта.

## Различия веток

- bonuspro/vendor-auth-fix: схема 0014 с аудитом смены покупателя; помощник обновления поддерживает переход с рабочей 0013.
  Поиск новых заказов и повторная сверка известных заказов выполняются worker.
  Эта ветка не содержит принимающего REMAP webhook inbox и потоков основной ветки.
- bonuspro/rebuild: схема 0016. Дополнительно содержит постоянный inbox вебхуков,
  индексы связанных документов, инкрементальные проверки и повторный полный поиск,
  а также worker pool. Уведомление быстро сохраняется и получает 204; работа с REMAP
  и финансовый пересчёт выполняются отдельно. requestId обеспечивает дедупликацию.
  Вебхуки — подсказки, доказательством остаются прочитанные документы.

МойСклад ожидает ответ на webhook за 1500 мс и делает лишь ограниченные повторы.
В основной ветке предусмотрены ограниченные таймауты БД на приёме и сверка
посредством polling при пропуске уведомлений. На бесплатном тарифе МойСклад
вебхуки не отправляются; сам факт наличия разрешения не гарантирует доставку.
Публичный статус не подтверждает, что worker действительно запущен на VPS.

Нельзя подставлять основной образ схемы 0016 поверх совместимой базы. В ветке
bonuspro/vendor-auth-fix update_cabinet.py проверяет резервную копию и миграцию
0013→0014 в отдельной БД до остановки приложения и обновления рабочей базы.
После открытия HTTPS автоматический откат схемы запрещён. finish_release.py
последовательно обновляет app и worker и выполняет read-only проверку аккаунта;
он не включает программу, не меняет дату начала начислений и не подтверждает
выполнение финансовой приёмки.

## Поддерживаемый режим и ограничения

Это границы текущей реализации, а не успешно пройденные сценарии:

- Списание в сохранённом проведённом заказе KZT до создания связанных оплат и
  отгрузок. При существующих документах новое списание блокируется.
- НДС включён в цену либо отключён. Исключённый из цены НДС и отрицательная
  процентная скидка (наценка) не поддерживаются для бонусного расчёта.
- Сначала подбирается точная процентная скидка. Если её нельзя выразить с
  точностью МойСклад, допускается уменьшение цены товара в целых денежных
  minor units с сохранением обычной скидки. Итог каждой строки обязан точно
  совпасть с распределённой суммой бонусов. Непредставимый итог или объединение
  разных исходных условий строк, нарушающее однозначность возврата, блокирует списание
  до резерва; денежное расхождение не округляется.
- Платёж, распределённый только на счёт покупателю (invoiceout), не считается
  оплатой заказа автоматически: требуется проверяемая связь с заказом/отгрузкой.
- Несоответствие корзин заказа и отгрузки не считается полной отгрузкой, даже
  если итоговые суммы совпадают. Удалённый или изменённый документ требует сверки.
- Ограничены размеры коллекций и графа документов; превышение не даёт
  разрешения рассчитать бонусы по усечённым данным.
- Wallet/POS находятся за границами этого выпуска.

## Автоматическая и реальная проверка

CI проверяет арифметику, PostgreSQL/RLS/конкуренцию, lifecycle, HTTP-контракты,
состояния виджета в Chromium, сборку и реальные HTTP-ответы контейнера,
повтор миграции и зависимости. Основная ветка также проверяет XSD дескриптора
и HTTPS-конфигурацию. Проверки HTTP используют синтетический провайдер;
скриншоты интерфейса используют синтетические остатки и заказы.

До передачи заказчику нужно зафиксировать на конкретном развёрнутом образе:

1. Установку/обновление дескриптора и открытие кабинета/виджета без ошибок.
2. Реальный баланс контрагента, резерв, применение, сохранение и отсутствие дубля
   после обновления страницы и открытия второго окна.
3. Покупку с услугой доставки: начисления нет до полной оплаты и полной отгрузки;
   после них одно начисление только по товарам.
4. Частичный и полный возврат; недостаток бонусов — дело администратору.
5. Работающий worker, догоняющий очередь после перезапуска; состояние обновления
   документов не остаётся незамеченным.
6. Реальные права кассира/администратора, экспорт/импорт нужных остатков,
   восстановление резервной копии и назначенный ответственный за мониторинг.

Числа прохождения CI и SHA указываются в PR и результатах конкретного запуска.
Ни этот документ, ни HTTP /health/ready не заменяют перечисленную приёмку.
